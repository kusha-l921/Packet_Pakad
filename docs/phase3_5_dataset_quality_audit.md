# Phase 3.5 — Dataset Quality, Label Integrity, and Evaluation Correction Report

## 1. Executive Summary

During the Phase 3 audit of real PCAP-derived encrypted traffic data, two critical scientific issues were uncovered:
1. **Scenario-to-Flow Label Leakage & Contamination**: 24 real-world PCAP files labeled at the capture level with application scenarios (`file_transfer`, `interactive`, `streaming`, `voip`, `web`) actually contained hundreds of background OS noise flows (LLMNR, mDNS, NetBIOS, ARP, local broadcast, infrastructure DNS, and collateral HTTP browsing). These background flows inherited the scenario label, polluting the training data and creating identical feature vectors with conflicting labels (e.g., identical 2-packet LLMNR vectors labeled as both `interactive` and `file_transfer`).
2. **Evaluation Over-Claiming (Capture Diversity Inequity)**: While classes like `web` (12 captures) and `interactive` (4 capture groups) had genuine capture-group diversity, classes like `streaming` (1 capture) and `voip` (1 capture) had only a single source capture. Splitting single-capture flows into train and test sets cannot be claimed as "independent capture-group isolation" or "zero capture overlap."

Phase 3.5 systematically resolves both issues **without replacing the ML architecture, without changing the 25-feature schema (`FEATURE_SCHEMA_VERSION = "1.0"`), and without silently discarding data**.

---

## 2. Why Scenario-Level PCAP Labels Create Flow-Level Label Problems

In network traffic capture environments, recording an application scenario (such as an SCP file transfer or an AIM chat session) captures all packets traversing the host network interface. Consequently:
- The operating system continually issues local name resolution requests (LLMNR on UDP 5355, mDNS on UDP 5353, NetBIOS on UDP 137/138).
- Discovery protocols broadcast periodic pulses (Dropbox LAN sync on UDP 17500, NTP time synchronization on UDP 123, SSDP on UDP 1900, DHCP on UDP 546/547).
- Layer-2 frames (ARP) and infrastructure DNS lookups (UDP 53) occur concurrently.
- User activity during long captures often includes incidental, collateral actions (such as visiting an HTTP webpage while preparing an SCP session).

When a pipeline blindly assigns `pcap.scenario_label` to every bidirectional flow reconstructed from that capture, **every background UDP broadcast inherits the high-level application label**.
- A 2-packet Windows LLMNR broadcast inside `aim_chat_3a.pcap` becomes labeled `interactive`.
- An identical 2-packet Windows LLMNR broadcast inside `scp1_sample.pcapng` becomes labeled `file_transfer`.

This introduces cross-label feature conflicts, misguides gradient updates during ML optimization, and degrades the scientific validity of the model.

## 4. Flow Relevance Policy

The `FlowRelevancePolicy` (implemented in `person2_engine/src/flow_filter.py`) defines an explicit, deterministic contract governing whether an extracted flow qualifies for ML training.

```
PCAP Input Capture
        ↓
Phase 1 Packet Analysis & Phase 2 Flow Builder
        ↓
Extracted Flow (25 Statistical Features)
        ↓
Flow Relevance Policy Evaluation:
  [1] Is flow ARP or non-IP? ───────────────► EXCLUDE: NON_IP_LAYER2
  [2] Is port 5355 (LLMNR)? ────────────────► EXCLUDE: BACKGROUND_LLMNR
  [3] Is port 5353 (mDNS)? ─────────────────► EXCLUDE: BACKGROUND_MDNS
  [4] Is port 137-139 (NetBIOS)? ───────────► EXCLUDE: BACKGROUND_NETBIOS
  [5] Is port 53 (DNS lookup)? ─────────────► EXCLUDE: BACKGROUND_INFRASTRUCTURE_DNS
  [6] Is discovery (NTP/SSDP/Dropbox)? ─────► EXCLUDE: BACKGROUND_LOCAL_DISCOVERY
  [7] Is destination multicast/broadcast? ──► EXCLUDE: BACKGROUND_MULTICAST_BROADCAST
  [8] Is collateral non-scenario traffic? ──► EXCLUDE: COLLATERAL_NON_SCENARIO_TRAFFIC
        ↓ PASS ALL RULES
  ELIGIBLE SCENARIO FLOW (Level 2)
```

All rules are modular and configurable via boolean parameters (`exclude_llmnr_mdns`, `exclude_netbios`, `exclude_multicast_broadcast`, `exclude_infrastructure_dns`, `exclude_local_discovery`, `exclude_non_ip`, `exclude_collateral_services`).

## 5. Label Conflict Elimination

### Analysis of the Conflict
During the Phase 3 audit, identical 2-packet feature vectors (`[2.0, 2.0, 0.0, 128.0, 128.0, 0.0, 64.0, 64.0, ...]`) appeared under conflicting labels:
- `interactive` from `aim_chat_3a.pcap`
- `file_transfer` from `scp1_sample.pcapng`

### Root Cause Proven
Forensic inspection of the underlying packet records proved that both flows were standard Windows OS LLMNR name resolution queries sent to multicast IP `224.0.0.252` on port `5355`. Neither flow had any connection to AIM chat or SCP file transfer.

### Resolution
With `FlowRelevancePolicy` active:
- Both LLMNR flows are categorized under `BACKGROUND_LLMNR`.
- They are excluded from Level 2 model training.
- **Cross-label conflict vectors dropped from 2 to exactly 0**.

## 7. Train/Test Evaluation Strategy & Capture Diversity

### 7.1 Group-Isolated vs. Within-Capture Holdout
Prior evaluations claimed "capture-group isolation" across the entire dataset. In reality:

1. **`GROUP_ISOLATED`**: Training and test flows originate from strictly disjoint capture groups. Models are tested on sessions from unseen network captures.
2. **`WITHIN_CAPTURE_HOLDOUT`**: Training and test flows originate from the *same* physical capture group because no independent second capture exists in the dataset.

### 7.2 Dataset Sufficiency per Class

| Class | Independent Captures | Capture Groups | Raw Flows | Model-Eligible Flows | Assigned Evaluation Mode | Sufficiency Status |
| :--- | :---: | :---: | :---: | :---: | :--- | :--- |
| `interactive` | 8 | 4 | 487 | 108 | `GROUP_ISOLATED` | **SUFFICIENT** |
| `web` | 12 | 12 | 14 | 14 | `GROUP_ISOLATED` | **SUFFICIENT** |
| `file_transfer` | 2 | 2 | 468 | 3 | `GROUP_ISOLATED` | **LIMITED SAMPLE SIZE** (n=3) |
| `streaming` | 1 | 1 | 62 | 58 | `WITHIN_CAPTURE_HOLDOUT` | **INSUFFICIENT INDEPENDENT CAPTURE DIVERSITY** |
| `voip` | 1 | 1 | 111 | 70 | `WITHIN_CAPTURE_HOLDOUT` | **INSUFFICIENT INDEPENDENT CAPTURE DIVERSITY** |

### 7.3 Overall Evaluation Strategy
The evaluation engine now explicitly separates metrics into:
- `OVERALL_MIXED_EVALUATION`: Aggregate performance across all classes.
- `[STRICT_GROUP_EVALUATION]`: Performance calculated exclusively on test samples from `GROUP_ISOLATED` classes (`interactive`, `web`, `file_transfer`).
- `[WITHIN_CAPTURE_EVALUATION]`: Performance calculated on test samples from `WITHIN_CAPTURE_HOLDOUT` classes (`streaming`, `voip`), accompanied by an explicit warning detailing the limitation.

## 10. Future Person 1 IPsec Data Compatibility

Phase 3.5 is architected to transition seamlessly when Person 1 delivers genuine IPsec / StrongSwan PCAPs:
1. **Manifest Contract**: Future manifests simply specify `source_dataset: "person1_ipsec"`, endpoint pairs, and scenario labels.
2. **Relevance Policy Adaptability**: IPsec tunnel traffic uses ESP (protocol 50) or UDP 4500 NAT-Traversal. The `FlowRelevancePolicy` can accept IPsec tunnel gateway addresses to cleanly distinguish encapsulated payload flows from non-encapsulated management traffic.
3. **No Code Changes in ML Pipeline**: The 25-feature vector, model trainer, evaluator, inference engine, and Phase 4 security analyzer remain completely unchanged.
