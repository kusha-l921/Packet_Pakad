# Phase 4 — AI Analysis, Security Assessment & Integration Output

## 1. Overview: What Phase 4 Does

Phase 4 is the **AI Security Assessment and Explainability Layer** of the network traffic analysis pipeline. It bridges the technical output of machine learning models (Phase 3) and statistical flow features (Phase 2) with high-level, human-understandable security insights.

The end-to-end pipeline operates as follows:

```
PCAP / PCAPNG
      ↓
Phase 1 — Packet Analysis and IPsec Detection
      ↓
Phase 2 — Bidirectional Flow Construction & 25 Statistical Features
      ↓
Phase 3 — Lightweight Tabular Machine Learning Classification
      ↓
Phase 4 — Behavioral Analysis, Security Assessment & Integration Output
      ↓
Person 3 Dashboard, Scoring System & Incident Reports
```

> [!IMPORTANT]
> **System Capability & Limitation Statement**:
> The current Phase 4 security assessment is an explainable behavioral and heuristic risk analysis system. It identifies statistically unusual traffic characteristics and configurable risk indicators without decrypting payloads. It does not independently confirm that a flow represents a cyber attack, malicious activity, or an intrusion. Risk indicators should be interpreted in the context of the deployment environment and expected baseline traffic.

Phase 4 evaluates every flow against observable behavioral rules, computes a calibrated risk score (0–100), isolates anomalous indicators, exposes model feature importances, generates factual narrative explanations, and aggregates capture-level summaries into an integration-ready JSON schema.

---

## 2. Decoupling Traffic Classification from Security Risk

A foundational scientific principle of this system is the **strict separation between traffic classification and security assessment**:

* **Traffic Classification** answers: *"What does this encrypted flow statistically resemble based on known training patterns?"* (e.g., Web, Video, VoIP, File Transfer, Interactive).
* **Security Risk Assessment** answers: *"Are there observable behavioral patterns in this flow that warrant operator attention?"* (e.g., extreme upload volume, packet rate bursts, uncoordinated periodicity).

### Critical Ground Rules
1. **Application types are NOT threat verdicts**:
   * File transfer traffic is **not** inherently an attack.
   * Video streaming is **not** malicious.
2. **Confidence is NOT risk**:
   * Low model confidence does **not** automatically indicate malware or malicious activity.
   * High model confidence does **not** guarantee traffic is benign.
3. **Indicators are observable anomalies, NOT proof of attack**:
   * All indicators are evidence-backed behavioral signals (e.g., a high-volume outbound data transfer). Whether that transfer represents legitimate cloud backup or unauthorized data exfiltration requires context from Person 3's scoring and policy engine.

---

## 3. What Prediction Confidence Means

In Phase 3 ML classification, the model computes class probabilities using soft probability distributions (e.g., softmax or decision tree leaf voting). Confidence is defined as the maximum posterior probability:

$$\text{Confidence} = \max_{c \in C} P(\text{class} = c \mid \mathbf{x})$$

Phase 4 defines three deterministic, configurable confidence tiers:

| Tier | Confidence Range | Interpretation |
|---|---|---|
| **HIGH** | $\ge 0.80$ (80%–100%) | The flow's statistical feature profile strongly matches a category known to the model. |
| **MEDIUM** | $0.50 \le c < 0.80$ (50%–79.9%) | The flow shares characteristics with known categories, but exhibits overlapping traits with neighboring classes. |
| **LOW** | $< 0.50$ (< 50%) | The flow does not strongly resemble any category in the model's training library. |

---

## 4. What Low Confidence Actually Means

When a flow receives **LOW confidence**, it means:

> **"The statistical profile of this flow does not conform to the distributions observed in the model's current training dataset."**

This can happen for benign reasons:
* The user is using an application not present in the ISCXVPN2016 dataset (e.g., modern Zoom, Discord, custom API sync).
* The network connection experienced abnormal packet pacing or jitter.
* The flow is encrypted under an encapsulation protocol (such as IPsec ESP) whose outer packet shapes differ from the TLS/HTTPS proxy traffic used in the current model.

Phase 4 flags this via the `model_uncertainty` flag `LOW_CLASSIFICATION_CONFIDENCE`, contributing exactly 0 points to the behavioral risk score. Model uncertainty is reported independently and is not treated as evidence of elevated security risk.

## 5. Behavioral Observations and Security Indicators

### Behavioral Observations (Phase 2 Feature Rules)
Generated by `BehaviorEngine` without payload decryption:

* `HIGH_PACKET_RATE`: Flow rate $\ge 100$ packets/second.
* `HIGH_BYTE_THROUGHPUT`: Throughput $\ge 500\text{ KB/s}$ ($500{,}000\text{ bytes/second}$).
* `HIGH_DIRECTIONAL_ASYMMETRY`: One direction accounts for $\ge 85\%$ of total byte volume.
* `ASYMMETRIC_UPLOAD_PATTERN`: Forward bytes $\ge 85\%$ of flow and total volume $\ge 50\text{ KB}$.
* `ASYMMETRIC_DOWNLOAD_PATTERN`: Backward bytes $\ge 85\%$ of flow and total volume $\ge 50\text{ KB}$.
* `HIGH_PACKET_SIZE_VARIANCE`: Packet size standard deviation $> 400\text{ bytes}$.
* `LOW_PACKET_SIZE_VARIANCE`: Packet size standard deviation $< 50\text{ bytes}$ (uniform packet sizing).
* `PERIODIC_TRAFFIC_PATTERN`: Inter-arrival time standard deviation $\le 0.05\text{ seconds}$ with mean $> 0.01\text{ seconds}$ (beaconing or fixed pacing).
* `LONG_DURATION_FLOW`: Flow duration $\ge 300\text{ seconds}$ (5 minutes).
* `SHORT_BURSTY_FLOW`: Duration $\le 2.0\text{ seconds}$, packet rate $\ge 50\text{ pkts/sec}$, and packet count $\ge 6$.
* `HIGH_TRAFFIC_BURST`: $\ge 100$ packets in a single 1-second window, or $> 70\%$ of packets occurring in the peak 1-second window.

### Security Indicators (Phase 4 Indicator Engine)
Generated by `IndicatorEngine`, each indicator carries deterministic severity, point contribution, human-readable rationale, and supporting feature values:

| Indicator ID | Severity | Points | Trigger Condition | Rationale |
|---|---|---|---|---|
| `UNUSUAL_HIGH_UPLOAD_VOLUME` | HIGH | 25 | $\text{forward\_bytes} \ge 200{,}000$ and $\text{ratio} \ge 0.85$ | Significant bulk outbound transmission with high directional asymmetry. |
| `UNUSUAL_HIGH_PACKET_RATE` | MEDIUM | 20 | $\text{packets\_per\_second} \ge 250$ | High packet transmission frequency over flow duration. |
| `UNUSUAL_BURST_ACTIVITY` | MEDIUM | 15 | Peak second $\ge 100$ pkts and $\ge 70\%$ of flow | Abrupt transmission spike concentrated in a short time window. |
| `LONG_LIVED_HIGH_VOLUME_FLOW` | MEDIUM | 15 | Duration $\ge 600\text{s}$ and volume $\ge 500\text{ KB}$ | Persistent, long-duration session sustaining heavy data exchange. |
| `PERIODIC_LOW_VOLUME_ACTIVITY` | LOW | 10 | Volume $\le 5\text{ KB}$, $\ge 15$ pkts, $\text{std\_iat} \le 0.05\text{s}$ | Regularly paced low-volume pacing resembling automated beaconing or keep-alives. |
| `LOW_CLASSIFICATION_CONFIDENCE` | INFO | 0 | Confidence $< 0.50$ | Model uncertainty flag; traffic does not strongly resemble known categories (0 risk points). |
| `STRONG_DIRECTIONAL_ASYMMETRY` | LOW | 10 | Volume $\ge 20\text{ KB}$ and unidirectional ratio $\ge 0.95$ | Near-unidirectional data flow with minimal reverse acknowledgment. |

## 6. How the Risk Score is Calculated

The flow risk score is an **explainable additive model**:

$$\text{Risk Score} = \min\left(100, \sum_{i \in \text{Triggered Indicators}} \text{Points}(i)\right)$$

### Key Properties
1. **Fully Traceable**: Every point added to the score corresponds to a specific indicator in `score_contributions`.
2. **Clamped Bounds**: The score is strictly bounded between **0** and **100**.
3. **Zero False Baselines**: A completely benign or quiet flow triggers zero indicators, yielding a risk score of **0**.
4. **No Arbitrary ML Multipliers**: The traffic category does **not** arbitrarily multiply or dictate the score.

---

## 7. Deterministic Risk Levels

The numerical risk score maps to four qualitative risk tiers:

| Tier | Score Range | Operational Meaning |
|---|---|---|
| **LOW** | 0 – 24 | Baseline network traffic. No significant anomalous behavior detected. Normal handling. |
| **MEDIUM** | 25 – 49 | Minor behavioral deviations (e.g., low classification confidence, moderate asymmetry). Worth secondary monitoring. |
| **HIGH** | 50 – 74 | Multiple compounding behavioral anomalies (e.g., high upload volume combined with high packet rates). Operator review advised. |
| **CRITICAL** | 75 – 100 | Severe behavioral divergence across multiple metrics (e.g., burst activity, massive outbound transfer, unclassified profile). Immediate triage recommended. |

> [!NOTE]
> These tiers reflect **observable statistical risk indicators**, not confirmed cyberattacks.

---

## 8. Capture-Level Aggregation & Scoring

Simply taking the arithmetic mean of all flow risk scores creates an **aggregation dilution flaw**: in a capture containing 1,000 normal flows (score 0) and 1 critical flow (score 85), the simple average would be $< 0.1$, obscuring the threat.

Phase 4 resolves this using an **intelligent percentile-blend aggregation**:

$$\text{Blended Score} = \text{round}(0.70 \times P_{90} + 0.30 \times \mu)$$

* If any individual flow reaches **CRITICAL** risk ($\ge 75$), the overall capture score will reflect the critical presence:

$$\text{Overall Score} = \max(\text{Max Score}, \text{Blended Score})$$

This guarantees that an active security incident is never diluted by benign background traffic.

## 10. Forward Compatibility with Person 1's StrongSwan IPsec PCAPs

Phase 4 is designed to analyze future Person 1 IPsec PCAPs without architectural changes:

1. **Protocol 50 (ESP) & Protocol 51 (AH)**:
   * Handled by Phase 1 and grouped into bidirectional flows by Phase 2's `FlowKey.create()`.
   * Outer ESP headers (SPI, sequence numbers) are analyzed without payload decryption.
2. **25 Statistical Features**:
   * Features such as packet sizes, inter-arrival times, burst ratios, and directional asymmetry remain valid regardless of whether payload encryption is TLS or ESP.
3. **Model Retraining with StrongSwan Manifests**:
   * When Person 1 captures labeled StrongSwan IPsec PCAPs, run:
     ```bash
     python main.py --extract-manifest --manifest datasets/manifests/person1_ipsec_manifest.json
     python main.py --train --dataset datasets/processed/strongswan_flows.csv
     ```
   * The new model registers in `models/registry/`. Phase 4 immediately utilizes the updated model without changing indicator rules, scoring formulas, or Person 3's JSON schema contract.
